# AGENTS.md

The role of this file is to describe common mistakes and points of confusion agents might encounter as they work in this project.

If you ever encounter something in the project that surprises you, please alert the developer working with you and update this file to help prevent future agents from having the same issue.

## Greenfield Project

This project is super greenfield. It has no users yet, no real data, etc. Be ruthless about eliminating tech debt. Make whatever changes you want and don’t worry about it, we’ll figure it out when we ship.

## Verification

- `npm test -w @nc-medicaid/agent` is not enough after changing tool schemas or API payload shapes. The Vitest suite can still pass while `npm run build -w @nc-medicaid/agent` fails on null-vs-undefined or output-schema type mismatches. Run both.
- The agent CLI/runtime does not get `.env` values from `tsx` or `npm exec` automatically. The real entrypoints now import [`load-env.ts`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/agent/src/load-env.ts) to hydrate `process.env` from repo/package `.env` files, but ad hoc one-off `node` / `tsx -e` commands still need to import that loader or manually export env vars first.
- The web package previously got imported with its own embedded `.git` directory under [`packages/web`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/web). If a package is ever copied in from a standalone repo again, remove the nested `.git` immediately or Git status/history inside that package will diverge from the monorepo and confuse tooling.
- `uv run` for the pipeline package must be run from [`packages/pipeline`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline), not the monorepo root. From the repo root, `uv` does not pick up `packages/pipeline/pyproject.toml`, so flags like `--extra dev` appear to succeed but do not install or expose tools like `pytest`.
- `uv run python -m pipeline.cli parse` caches by source hash plus `PARSE_CACHE_VERSION`. If you change parser logic and need existing artifacts regenerated immediately, either bump `PARSE_CACHE_VERSION` in [`converter.py`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline/src/pipeline/parse/converter.py) or run parse with `--force`; otherwise the pipeline will skip unchanged source files.
- The parse loop now isolates PDF work per file and defaults `PIPELINE_PARSE_TIMEOUT_SECONDS` to `600`. If one pathological PDF keeps stalling a family ingest, do not wait forever; let it time out into a `parse_exception`, or raise/lower the timeout explicitly with that env var.
- Answer eval CLI runs should use an isolated observability DB path, typically `:memory:` via `MASTRA_OBSERVABILITY_PATH`, rather than the default `mastra.duckdb`. Otherwise one timed-out or crashed CLI run can leave a DuckDB lock behind and poison the next eval question.
- `packages/pipeline/data/eval-results` currently mixes durable benchmark snapshots with many accidental one-off / partial eval outputs. When deciding what to commit, prefer full-run milestone snapshots and avoid adding single-question or exploratory JSONs unless there is a specific debugging reason to preserve them.
- The monorepo GitHub Actions workflow is not Node-only in practice. Before running root `lint` or `test` in CI, provision the pipeline environment (currently `npm run setup -w @nc-medicaid/pipeline` after Python setup) or `@nc-medicaid/pipeline` will fail on missing `.venv/bin/ruff` / pytest.
- Single-question answer evals can finish the agent and judge successfully but still crash while saving results if any per-question retrieval metrics are `None`. In [`results.py`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline/src/pipeline/eval/results.py), keep the `by_difficulty` / `by_category` rollups filtered to the same scorable subset used for the top-level aggregate.
- Full answer-eval CLI runs can silently burn extra OpenAI quota through non-essential agent helpers such as observational memory, prompt-injection detection, and hallucination verification. For CLI/eval runs, prefer disabling those extra processors/memory layers so quota is spent on the main answering model and the judge, not on sidecar checks.
- Answer-eval judge variance is high enough now that a single fresh `2/3` is not always a structural regression. If a question was recently green and the current frame/routing output still looks clean, rerun the targeted answer eval and compare saved explanations across runs before changing retrieval or prompt/planner logic.
- When wrapping the agent CLI in answer eval, killing only the parent process on timeout is not enough. The `tsx`/Node subprocess tree can keep running and hold the DuckDB lock; start the subprocess in its own process group and kill the whole group on timeout.
- Full mixed-corpus retrieval eval is heavy enough that a single giant Python→TypeScript retrieval batch can time out even when the graph build is healthy. Prefer the chunked retrieval-eval path in [`retrieval.py`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline/src/pipeline/eval/levels/retrieval.py), which logs progress in small batches instead of sending the whole dataset through one opaque CLI call.
- The crawler registry stores `documents.local_path` relative to `packages/crawler/data/documents`, while older parse sidecars record absolute `source_pdf` paths. Any audit or reconciliation code that joins registry/download/parse state must normalize both forms first, or it will double-count parsed files as orphaned artifacts.
- Official NC Medicaid attachment links often differ only by URL fragment (for example `#page=...` or anchor IDs). Strip `URL.hash` in crawler URL canonicalization or the registry will treat the same managed-care contract PDF as multiple documents.
- The relative-vs-absolute path issue also affects graph loading, not just audit. When a source family has PDF/XLSX companions with the same slug/title (common in `fee_schedule`), falling back from an absolute sidecar path to fuzzy stem matching can attach the PDF parse to the XLSX registry row. Normalize to the relative crawler `local_path` first so companion files keep distinct `source_url` identities.
- Legacy parse sidecars created before the corpus-audit refactor do not include `source_file`, `parse_status`, `quality_flags`, or `answer_ready`. Treat missing `parse_status` as a legacy successful parse by default, and at minimum derive `zero_section_parse` from `section_count == 0` when backfilling audit state.
- Do not run multiple `uv run python -m pipeline.cli load --source ...` commands concurrently against the same Neo4j instance. `ensure_schema()` can race across sessions and Neo4j will raise `EquivalentSchemaRuleAlreadyExists` even though the end state is logically idempotent. Load source families sequentially unless schema setup is hardened.
- The new supporting source families are much larger and messier than the fixture set implies. `fee_schedule` discovery currently yields about 2,000 documents, while `managed_care_guidance` yields hundreds of mixed PDFs plus unsupported `.pptx` files and oversized attachments. Treat those as staged ingests and rely on `audit-corpus` to track partial progress instead of assuming one crawl/parse/load pass will finish quickly.
- `managed_care_contract` is not adequately covered by the older provider-contracting landing pages alone. The high-value contract/amendment PDFs live off [`health-plan-contact-information`](https://medicaid.ncdhhs.gov/health-plan-contact-information), so discovery for that family should traverse that page and related contract detail pages rather than stopping at shallow guidance/index content.
- For `dhhs_policy`, `policy_number` is metadata, not a unique identity key. Change notices, translated notices, appendices, and annual revisions often share the same policy number. Use `source_url` as the unique document discriminator in `build_document_id(...)`, and only keep `policy_number` as readable metadata.
- Do not infer a DHHS document's `policy_number` from titles that are change notices (`CHANGE NOTICE FOR MANUAL NO. ...`). Those titles mention the policy they amend, not the notice's own identity. Treating that mention as the notice's `policy_number` pollutes policy-number lookup and amendment resolution.
- Repeated section numbers inside one document are real in the parsed DHHS corpus (for example repeated `Attachment B` headers). Internal `Section.id` values need a deterministic duplicate suffix; `document_id + section_number` alone is not always unique.
- When inferring coverage-routing documents from retrieval hits, do not blindly keep every document returned by `lookupPolicyInternal(policyNumber)`. One inferred policy number can expand to several related documents (for example the `MA-2270` family) and swamp the sibling policies you actually want. Prefer the top current document per inferred policy number before doing sibling/variant selection.
- In retrieval ranking, alias-based policy hints are helpful for service questions (`CAP/DA` -> `3K-2`, `outpatient therapy` -> `10A`), but they can swamp the right evidence on federal-authority questions. When the query is clearly asking for federal statutory or regulatory authority, do not let program-name aliases override federal sources.
- The reverse is also true for managed-care contract questions: when the user explicitly asks what NC managed care contracts require, `managed_care_contract` should be the governing source and CFR/SSA should stay supporting unless the query explicitly asks for federal authority.
- For MLR federal-state questions like `q-021`, `resolveFederalAuthorityFrame(...)` must include `managed_care_contract` in the NC implementation search path. If that search is limited to SPA/manual-style sources, the answer degrades into SPA-only remittance language and misses the contract-based implementation details the eval expects.
- Some DHHS change notices currently parse into title-only sections with blank bodies. For temporal or amendment-history evals, prefer anchoring the golden evidence on the current manual's revision header (for example `REVISED ... CHANGE NO. 04-26`) when that is the only reliable parsed evidence for the latest amendment.
- For "latest change notice" answer work, do not infer what the newest amendment changed from a nearby current-manual section unless the change notice body or `changeSummary` explicitly connects that section to the amendment. A retrievable live section like `Mileage Effective (1/1/2026)` can sit near the current revision header without proving that the latest notice itself made that specific change.
- For "latest change notice" questions, the current manual/policy revision header is the authoritative recency signal when it conflicts with standalone change-notice titles. In the NEMT corpus, blank 2026 notice titles like `02-26` can appear in search even though the current MA-3550 header shows the newer `REVISED 03/16/2026 - CHANGE NO. 04-26`.
- For PCS reconsideration questions, retrieval can surface both [`3L`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline/data/golden/dataset.json) and [`3L-1`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline/data/golden/dataset.json) `Section 5.6` near the top because the section titles and timing language are effectively identical. Do not confidently rule one sibling policy out unless the user clearly specifies the setting.
- For outpatient pharmacy prior-authorization questions, search often ranks `Attachment C: Requesting Prior Authorization for Prescription Drugs` above the more substantively relevant `Pharmacy Prior Approval Drugs and Criteria` / `Attachment K`. The request-process attachment is useful for workflow, but the criteria attachment is the better source for when PA is actually required.
- Some clinical-policy telehealth rules live under unnumbered lettered headings rather than numbered sections. In the current graph, the key speech-therapy telehealth text for Policy 10A is on [`sec:doc:clinical_policy:10A:_s31`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline/data/golden/dataset.json) titled `e. Telehealth`, while the expected general telehealth section in Policy 1-H can be blank. For telehealth answer/debug work, do not assume the numbered `1-H` section is the best available source in the graph.
- Cross-ref eval should only assert relationships that the graph is expected to encode explicitly (`REFERENCES`, `REFERENCES_DOCUMENT`, `AMENDS`). Shared template text across policies and background federal authority that is not actually cited in the source document belong in supporting/federal evidence, not `cross_references`.
- The crawler `documents` registry does not store a normalized `source_format` column you can trust during downstream selection/routing. For fee-schedule canonicalization or any format-sensitive variant ranking, infer format from `local_path` (preferred) or `source_url` when the registry row itself omits it, or PDF/XLSX companions can be mis-ranked.
- Fee-schedule titles use multiple date styles, including `May, 2020` with a comma but no day. If you normalize variant families or dates from titles, make sure the parser handles month-comma-year forms or you will accidentally split one schedule family into separate `variant_group`s.
- Live retrieval smoke checks depend on Voyage query embeddings today. If `VOYAGE_API_KEY` is missing or unauthorized, the agent retrieval CLI will fail even when Neo4j and the corpus are healthy; use a custom `embedQuery` stub only for local debugging, and do not mistake that auth failure for a corpus regression.
- CAP/DA-style general eligibility questions can get over-narrowed by service-focus routing. For those, do not jump straight to `3.2.x` specific criteria or operational CAP sections like claim reimbursement/provider requirements; anchor the answer frame on the broader eligibility stack first (`2.1.1`, then `3.1`, then `3.2.1`), and use scope/age text only as supporting context when it is actually surfaced.
- Federal waiver-application questions can drift into procedural notice rules (`42 CFR 431.408`, and even unrelated Part 431 / Part 155 notice content) because the query mentions what the state must do before submission. Unless the user explicitly asks about public notice or hearings, keep the governing answer on the `1915(c)` / `42 CFR Part 441` waiver-request sections (`441.301`-`441.303`) and demote notice procedure to supporting or avoid.
- The live `42 CFR Part 441` corpus can surface both the older waiver-request numbering (`441.301`-`441.303`) and the newer parallel sections (`441.351`-`441.355`) for the same waiver-application concepts. For CAP/DA federal-authority work, treat both numbering families as valid primary waiver/application evidence instead of hard-coding only `441.30x`.
- Single full answer-eval runs wobble enough that one-off `2/3` misses are not a reliable routing signal by themselves. Before patching answer logic for a new miss, check recent full runs with `uv run python -m pipeline.cli eval-answer-stability --last N --full-only` from [`packages/pipeline`](/Users/jkh/src/tries/2026-03-26-medicaid-agent/packages/pipeline) and prioritize questions that miss repeatedly.
- Congregate-setting PCS coverage questions can surface `5.4.x` assessment / referral workflow sections because they contain the word `eligibility`. For assisted-living / Adult Care Home coverage answers, prefer `3.2.1` + `3.3` + `4.2.1.2`, and demote `5.4.x` workflow sections unless the user explicitly asks about assessment or admission workflow.
- For negative yes/no coverage questions where the asked service is outside the policy’s scope (for example chiropractic under Policy `5B`), the best answer frame is usually the policy description/scope section (`2.1.1`) paired with the general not-covered section (`4.1`). Broader covered/not-covered sections like `3.1` or `4.2` can be accurate but still weaken evals if they replace the scope anchor.
- When answer quality work starts turning into policy-family prompt patches, stop and move that behavior into `resolveAnswerFrame` / `PolicyCorpus` instead. The agent prompt should stay limited to durable citation, amendment, and workflow rules.
- Railway agent deploys that run `npx mastra build --dir src` need the local `@nc-medicaid/policy-corpus` workspace present inside the Docker build context. If the Dockerfile only copies `packages/agent`, Mastra can fall back to trying `@nc-medicaid/policy-corpus@latest` from npm and fail with a 404 during the bundle install step.
