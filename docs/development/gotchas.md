# Project gotchas

Current guidance carried forward from main at `dc81a97`. When behavior changes, correct the affected lesson alongside the implementation.


- Parse inventory alone cannot find downloads that never created a `local_path`. Reconcile every non-removed registry row as well: September 2026 had 33 such failures (30 optional fee-schedule/guidance attachments and three required DHHS wrappers). `recovery-inventory` includes these and release preparation rejects missing required payloads before parsing or graph reset. The final complete inventory also exposed 283 existing optional parse exceptions, for 313 optional failures including downloads; report them separately without silently weakening source-family requirements.

- The corpus-job image pins Railway CLI 5.17.0, which has no `railway api` subcommand even though a newer workstation CLI does. Initial activation uses the public GraphQL API with the project token header; validate operational adapters against the production image, not just local CLI help.

- The crawler's historical `status='removed'` rows are not equivalent to evidence-backed retirement. `recovery-inventory` reports both active parse failures and removed sources without a durable retirement record; release preparation rejects either. In September 2026, checking only the nine recent parse failures hid 136 older undocumented exclusions. Do not grandfather those exclusions or create retirement evidence from a tombstone alone.

- The corpus release smoke must parse final verification events and released answer text. Response byte counts or the presence of source URLs can accept a withheld answer. Require a completed SSE stream, a passed/corrected outcome, and citations in the released text.
- A documented source retirement must survive rediscovery. Keep its SQLite evidence/history; only the guarded reactivation command may clear it after a fresh payload passes downloader checks. Repeated index links are not evidence that a missing attachment has returned.
- Production WorkOS test-account access tokens currently last five minutes. Mint one immediately before release smoke; an expiry preflight requiring the entire five-minute lifetime plus network overhead rejects every freshly issued token.

- The corpus-job image needs the versioned files under `packages/pipeline/data/golden` even though runtime corpus data must stay outside the Docker context. Preserve the targeted `.dockerignore` exceptions and the Dockerfile's dataset-validation check; a successful image build without those files only fails later at the release-evaluation stage.

- `npm test -w @nc-medicaid/agent` is not enough after changing tool schemas or API payload shapes. The Vitest suite can still pass while `npm run build -w @nc-medicaid/agent` fails on null-vs-undefined or output-schema type mismatches. Run both.
- Local multi-step chat runs against OpenAI Responses can fail with `400 Duplicate item found with id ...` even when `/health` is green. The failure mode is duplicated stored response/tool items in Mastra message history, which show up as repeated `item_reference` / `function_call_output` entries in the OpenAI request body. If this resurfaces, inspect the step-input messages before the model call and dedupe repeated tool/result history rather than debugging the web client.
- The agent CLI/runtime does not get `.env` values from `tsx` or `npm exec` automatically. The real entrypoints now import [`load-env.ts`](../../packages/agent/src/load-env.ts) to hydrate `process.env` from repo/package `.env` files, but ad hoc one-off `node` / `tsx -e` commands still need to import that loader or manually export env vars first.
- Railway `@nc-medicaid/agent` must watch BOTH `packages/agent/**` and `packages/policy-corpus/**` — the agent imports `@nc-medicaid/policy-corpus` and the Dockerfile copies it into the build context, so corpus-only changes need to trigger redeploys too. Set this in the Railway UI under the `agent` service → Settings → Watch Paths. If it's still narrower than that (historically it was `packages/agent/**` only), corpus changes will silently skip deploy with "No changes to watched files" even on manual `railway up` / `mcp__railway__deploy`.
- GitHub-triggered Railway deploys can fail before Docker logs appear even when the Dockerfile and source are healthy. When that happens, retry `@nc-medicaid/agent` from a clean detached `origin/main` worktree with `railway up --project 2a11b10b-43ea-4181-b975-da24adcc3322 --environment production --service '@nc-medicaid/agent' --ci`, then verify `/healthz` and run `npm run smoke:prod`; do not rescue deploys from a dirty or diverged local branch.
- The web package previously got imported with its own embedded `.git` directory under [`packages/web`](../../packages/web). If a package is ever copied in from a standalone repo again, remove the nested `.git` immediately or Git status/history inside that package will diverge from the monorepo and confuse tooling.
- `uv run` for the pipeline package must be run from [`packages/pipeline`](../../packages/pipeline), not the monorepo root. From the repo root, `uv` does not pick up `packages/pipeline/pyproject.toml`, so flags like `--extra dev` appear to succeed but do not install or expose tools like `pytest`.
- `uv run python -m pipeline.cli parse` caches by source hash plus `PARSE_CACHE_VERSION`. If you change parser logic and need existing artifacts regenerated immediately, either bump `PARSE_CACHE_VERSION` in [`converter.py`](../../packages/pipeline/src/pipeline/parse/converter.py) or run parse with `--force`; otherwise the pipeline will skip unchanged source files.
- The parse loop now isolates PDF work per file and defaults `PIPELINE_PARSE_TIMEOUT_SECONDS` to `600`. If one pathological PDF keeps stalling a family ingest, do not wait forever; let it time out into a `parse_exception`, or raise/lower the timeout explicitly with that env var.
- Fresh Python 3.11 `spawn` workers can inherit OpenCV's temporary package path from the parent. Keep the multiprocessing target in the minimal [`worker.py`](../../packages/pipeline/src/pipeline/parse/worker.py) bootstrap, which explicitly loads stdlib `typing` before importing the Docling converter; targeting the converter directly lets `cv2/typing` shadow stdlib and crashes every Railway parse worker.
- Force-terminating a `spawn` parser worker while Torch/RapidOCR is active can leave named POSIX semaphores registered with the parent's `multiprocessing.resource_tracker`—one per timed-out worker was observed in Railway. Preserve the unique per-worker semaphore prefix and ownership-scoped cleanup in `worker.py`/`converter.py`; changing only Queue/Pipe IPC does not prevent this leak, and a global `/dev/shm` before/after diff can unlink another process's live semaphore.
- The Railway corpus-job image needs Debian's `libgl1` even though parsing is headless. Docling imports OpenCV while parsing PDFs, and without `libGL.so.1` every PDF worker fails after startup. Keep the Dockerfile's build-time `.venv/bin/python -c "import cv2"` smoke check so missing native runtime libraries fail the image build instead of a corpus run.
- Answer eval CLI runs should use an isolated observability DB path, typically `:memory:` via `MASTRA_OBSERVABILITY_PATH`, rather than the default `mastra.duckdb`. Otherwise one timed-out or crashed CLI run can leave a DuckDB lock behind and poison the next eval question.
- `packages/pipeline/data/eval-results` currently mixes durable benchmark snapshots with many accidental one-off / partial eval outputs. When deciding what to commit, prefer full-run milestone snapshots and avoid adding single-question or exploratory JSONs unless there is a specific debugging reason to preserve them.
- The monorepo GitHub Actions workflow is not Node-only in practice. Before running root `lint` or `test` in CI, provision the pipeline environment (currently `npm run setup -w @nc-medicaid/pipeline` after Python setup) or `@nc-medicaid/pipeline` will fail on missing `.venv/bin/ruff` / pytest.
- The Playwright suite under [`e2e`](../../e2e) has its own `package-lock.json` and is not a root npm workspace. A root `npm ci` does not install `@playwright/test` there; run `npm ci` from `e2e/` before `npm run test:e2e` in a fresh checkout.
- Avoid broad `.gitignore` patterns like `coverage/` at the repo root when the codebase also has real source directories whose names start with `coverage` (for example [`packages/policy-corpus/src/frame/coverage-sections`](../../packages/policy-corpus/src/frame/coverage-sections)). Remote build systems can treat that ignore rule as a build-context exclude and silently drop source files even though Git tracks them; prefer anchored rules like `/coverage/` or package-specific output ignores.
- Single-question answer evals can finish the agent and judge successfully but still crash while saving results if any per-question retrieval metrics are `None`. In [`results.py`](../../packages/pipeline/src/pipeline/eval/results.py), keep the `by_difficulty` / `by_category` rollups filtered to the same scorable subset used for the top-level aggregate.
- Full answer-eval CLI runs still skip observational memory and prompt-injection detection to save quota, but the **hallucination verifier IS on** for CLI/eval so scores reflect what web users see. The CLI runner emits a `---VERIFIER---` JSON block on stdout that `extract_verifier_metadata()` captures into `per_question.verifier` in `*_answer.json`. Set `VERIFIER_ENABLED=false` in the agent env only for fast one-off debug runs where you want the raw pre-verifier answer.
- Answer-eval judge variance is high enough now that a single fresh `2/3` is not always a structural regression. If a question was recently green and the current frame/routing output still looks clean, rerun the targeted answer eval and compare saved explanations across runs before changing retrieval or prompt/planner logic.
- When wrapping the agent CLI in answer eval, killing only the parent process on timeout is not enough. The `tsx`/Node subprocess tree can keep running and hold the DuckDB lock; start the subprocess in its own process group and kill the whole group on timeout.
- Full mixed-corpus retrieval eval is heavy enough that a single giant Python→TypeScript retrieval batch can time out even when the graph build is healthy. Prefer the chunked retrieval-eval path in [`retrieval.py`](../../packages/pipeline/src/pipeline/eval/levels/retrieval.py), which logs progress in small batches instead of sending the whole dataset through one opaque CLI call.
- The crawler registry stores `documents.local_path` relative to `packages/crawler/data/documents`, while older parse sidecars record absolute `source_pdf` paths. Any audit or reconciliation code that joins registry/download/parse state must normalize both forms first, or it will double-count parsed files as orphaned artifacts.
- Official NC Medicaid attachment links often differ only by URL fragment (for example `#page=...` or anchor IDs). Strip `URL.hash` in crawler URL canonicalization or the registry will treat the same managed-care contract PDF as multiple documents.
- The relative-vs-absolute path issue also affects graph loading, not just audit. When a source family has PDF/XLSX companions with the same slug/title (common in `fee_schedule`), falling back from an absolute sidecar path to fuzzy stem matching can attach the PDF parse to the XLSX registry row. Normalize to the relative crawler `local_path` first so companion files keep distinct `source_url` identities.
- Legacy parse sidecars created before the corpus-audit refactor do not include `source_file`, `parse_status`, `quality_flags`, or `answer_ready`. Treat missing `parse_status` as a legacy successful parse by default, and at minimum derive `zero_section_parse` from `section_count == 0` when backfilling audit state.
- Do not run multiple `uv run python -m pipeline.cli load --source ...` commands concurrently against the same Neo4j instance. `ensure_schema()` can race across sessions and Neo4j will raise `EquivalentSchemaRuleAlreadyExists` even though the end state is logically idempotent. Load source families sequentially unless schema setup is hardened.
- The new supporting source families are much larger and messier than the fixture set implies. `fee_schedule` discovery currently yields about 2,000 documents, while `managed_care_guidance` yields hundreds of mixed PDFs plus unsupported `.pptx` files and oversized attachments. Treat those as staged ingests and rely on `audit-corpus` to track partial progress instead of assuming one crawl/parse/load pass will finish quickly.
- `managed_care_contract` is not adequately covered by the older provider-contracting landing pages alone. The high-value contract/amendment PDFs live off [`health-plan-contact-information`](https://medicaid.ncdhhs.gov/health-plan-contact-information), so discovery for that family should traverse that page and related contract detail pages rather than stopping at shallow guidance/index content.
- For `dhhs_policy`, `policy_number` is metadata, not a unique identity key. Change notices, translated notices, appendices, and annual revisions often share the same policy number. Use `source_url` as the unique document discriminator in `build_document_id(...)`, and only keep `policy_number` as readable metadata.
- Do not infer a DHHS document's `policy_number` from titles that are change notices (`CHANGE NOTICE FOR MANUAL NO. ...`). Those titles mention the policy they amend, not the notice's own identity. Treating that mention as the notice's `policy_number` pollutes policy-number lookup and amendment resolution.
- Repeated section numbers inside one document are real in the parsed DHHS corpus (for example repeated `Attachment B` headers). Internal `Section.id` values need a deterministic duplicate suffix; `document_id + section_number` alone is not always unique.
- When inferring coverage-routing documents from retrieval hits, do not blindly keep every document returned by `lookupPolicyInternal(policyNumber)`. One inferred policy number can expand to several related documents (for example the `MA-2270` family) and swamp the sibling policies you actually want. Prefer the top current document per inferred policy number before doing sibling/variant selection.
- In retrieval ranking, alias-based policy hints are helpful for service questions (`CAP/DA` -> `3K-2`, `outpatient therapy` -> `10A`), but they can swamp the right evidence on federal-authority questions. When the query is clearly asking for federal statutory or regulatory authority, do not let program-name aliases override federal sources.
- The reverse is also true for managed-care contract questions: when the user explicitly asks what NC managed care contracts require, `managed_care_contract` should be the governing source and CFR/SSA should stay supporting unless the query explicitly asks for federal authority.
- For MLR federal-state questions like `q-021`, `resolveFederalAuthorityFrame(...)` must include `managed_care_contract` in the NC implementation search path. If that search is limited to SPA/manual-style sources, the answer degrades into SPA-only remittance language and misses the contract-based implementation details the eval expects.
- Some DHHS change notices currently parse into title-only sections with blank bodies. For temporal or amendment-history evals, prefer anchoring the golden evidence on the current manual's revision header (for example `REVISED ... CHANGE NO. 04-26`) when that is the only reliable parsed evidence for the latest amendment.
- For "latest change notice" answer work, do not infer what the newest amendment changed from a nearby current-manual section unless the change notice body or `changeSummary` explicitly connects that section to the amendment. A retrievable live section like `Mileage Effective (1/1/2026)` can sit near the current revision header without proving that the latest notice itself made that specific change.
- For "latest change notice" questions, the current manual/policy revision header is the authoritative recency signal when it conflicts with standalone change-notice titles. In the NEMT corpus, blank 2026 notice titles like `02-26` can appear in search even though the current MA-3550 header shows the newer `REVISED 03/16/2026 - CHANGE NO. 04-26`.
- For PCS reconsideration questions, retrieval can surface both [`3L`](../../packages/pipeline/data/golden/dataset.json) and [`3L-1`](../../packages/pipeline/data/golden/dataset.json) `Section 5.6` near the top because the section titles and timing language are effectively identical. Do not confidently rule one sibling policy out unless the user clearly specifies the setting.
- For outpatient pharmacy prior-authorization questions, search often ranks `Attachment C: Requesting Prior Authorization for Prescription Drugs` above the more substantively relevant `Pharmacy Prior Approval Drugs and Criteria` / `Attachment K`. The request-process attachment is useful for workflow, but the criteria attachment is the better source for when PA is actually required.
- Some clinical-policy telehealth rules live under unnumbered lettered headings rather than numbered sections. In the current graph, the key speech-therapy telehealth text for Policy 10A is on [`sec:doc:clinical_policy:10A:_s31`](../../packages/pipeline/data/golden/dataset.json) titled `e. Telehealth`, while the expected general telehealth section in Policy 1-H can be blank. For telehealth answer/debug work, do not assume the numbered `1-H` section is the best available source in the graph.
- Cross-ref eval should only assert relationships that the graph is expected to encode explicitly (`REFERENCES`, `REFERENCES_DOCUMENT`, `AMENDS`). Shared template text across policies and background federal authority that is not actually cited in the source document belong in supporting/federal evidence, not `cross_references`.
- The crawler `documents` registry does not store a normalized `source_format` column you can trust during downstream selection/routing. For fee-schedule canonicalization or any format-sensitive variant ranking, infer format from `local_path` (preferred) or `source_url` when the registry row itself omits it, or PDF/XLSX companions can be mis-ranked.
- Fee-schedule titles use multiple date styles, including `May, 2020` with a comma but no day. If you normalize variant families or dates from titles, make sure the parser handles month-comma-year forms or you will accidentally split one schedule family into separate `variant_group`s.
- Live retrieval smoke checks depend on Voyage query embeddings today. If `VOYAGE_API_KEY` is missing or unauthorized, the agent retrieval CLI will fail even when Neo4j and the corpus are healthy; use a custom `embedQuery` stub only for local debugging, and do not mistake that auth failure for a corpus regression.
- CAP/DA-style general eligibility questions can get over-narrowed by service-focus routing. For those, do not jump straight to `3.2.x` specific criteria or operational CAP sections like claim reimbursement/provider requirements; anchor the answer frame on the broader eligibility stack first (`2.1.1`, then `3.1`, then `3.2.1`), and use scope/age text only as supporting context when it is actually surfaced.
- Federal waiver-application questions can drift into procedural notice rules (`42 CFR 431.408`, and even unrelated Part 431 / Part 155 notice content) because the query mentions what the state must do before submission. Unless the user explicitly asks about public notice or hearings, keep the governing answer on the `1915(c)` / `42 CFR Part 441` waiver-request sections (`441.301`-`441.303`) and demote notice procedure to supporting or avoid.
- The live `42 CFR Part 441` corpus can surface both the older waiver-request numbering (`441.301`-`441.303`) and the newer parallel sections (`441.351`-`441.355`) for the same waiver-application concepts. For CAP/DA federal-authority work, treat both numbering families as valid primary waiver/application evidence instead of hard-coding only `441.30x`.
- Single full answer-eval runs wobble enough that one-off `2/3` misses are not a reliable routing signal by themselves. Before patching answer logic for a new miss, check recent full runs with `uv run python -m pipeline.cli eval-answer-stability --last N --full-only` from [`packages/pipeline`](../../packages/pipeline) and prioritize questions that miss repeatedly.
- Congregate-setting PCS coverage questions can surface `5.4.x` assessment / referral workflow sections because they contain the word `eligibility`. For assisted-living / Adult Care Home coverage answers, prefer `3.2.1` + `3.3` + `4.2.1.2`, and demote `5.4.x` workflow sections unless the user explicitly asks about assessment or admission workflow.
- For negative yes/no coverage questions where the asked service is outside the policy’s scope (for example chiropractic under Policy `5B`), the best answer frame is usually the policy description/scope section (`2.1.1`) paired with the general not-covered section (`4.1`). Broader covered/not-covered sections like `3.1` or `4.2` can be accurate but still weaken evals if they replace the scope anchor.
- When answer quality work starts turning into policy-family prompt patches, stop and move that behavior into `resolveAnswerFrame` / `PolicyCorpus` instead. The agent prompt should stay limited to durable citation, amendment, and workflow rules.
- Railway agent deploys that run `npx mastra build --dir src` need the local `@nc-medicaid/policy-corpus` workspace present inside the Docker build context. If the Dockerfile only copies `packages/agent`, Mastra can fall back to trying `@nc-medicaid/policy-corpus@latest` from npm and fail with a 404 during the bundle install step.
- Railway rejects Dockerfiles containing a `VOLUME` instruction, even though ordinary Docker and hosted CI image builds accept it. Persistent storage for `corpus-job` must be attached in Railway at `/data`; do not add `VOLUME ["/data"]` back to `packages/pipeline/Dockerfile`.
- A Railway service's private DNS name is independently generated and does not necessarily match the service display name. For the blue-green graph services, explicitly set the private DNS names to `neo4j-blue` and `neo4j-green` before using `bolt://neo4j-blue.railway.internal:7687` and `bolt://neo4j-green.railway.internal:7687`; otherwise the corpus job fails with an unresolvable host even though both services appear online.
- Railway CLI `redeploy` returns after enqueueing a deployment, not after the replacement instance is ready. A probe issued immediately afterward can connect to the old volume-backed Neo4j instance just before Railway stops it. Use `redeploy --json`, poll that returned deployment ID to `SUCCESS`, and only then run graph readiness before starting a reset/load.
- Railway Object Storage still contains the workstation-era corpus backup layout at top-level `crawler/` and `pipeline/`, while hosted releases write `corpus/current/...`. Restore must prefer `corpus/current`, retain the tested legacy fallback (including selecting the latest dated `crawler/registry/crawler-*.db` snapshot), and test for a non-empty `rclone lsf` result because an absent S3 prefix can still exit successfully.

- Railway config-as-code overrides the start command shown by the service-config tool. For supervised corpus maintenance, set the config path explicitly to `/deploy/railway/corpus-maintenance.json` and upload clean source; redeploying a previous upload can reuse its previous config-file metadata. Inspect deployment metadata (`configFile`, `fileServiceManifest`, and `serviceManifest`) before assuming an override applied. A cron deployment can report `SUCCESS` with its instance still `CREATED`; verify the actual instance and process. Restore `/packages/pipeline/railway.json` and scheduled mode only when cutover is ready.

- Docling retains real text inside `PictureItem` children and in `checkbox_selected` / `checkbox_unselected` items. Use `iterate_items(traverse_pictures=True)` and include both checkbox labels in parser quality checks and graph section extraction, or region maps and application checklists can be incorrectly classified as blank. Valid v4/v5 cached payloads retain these items and can be reused by the corrected loader; failed/blank parses must be retried.

- The pinned corpus-job npm can install successfully while `npx` fails at runtime with `minipass-sized` / `Class extends value undefined`. Invoke the workspace-installed runner with `node node_modules/tsx/dist/cli.mjs` for production crawl/evaluation jobs; this also avoids fetching a missing runner implicitly. Verify that runner during the image build.
- The five beneficiary-guidance golden cases were added with obsolete `url-...` IDs after graph identity moved to URL-derived hashes. Official HTML headings also moved in August 2026. For HTML evidence, compute document IDs with `pipeline.identity.build_document_id` and inspect the actual parsed section body before recording an ordinal section ID; a valid schema alone does not prove that a golden reference exists or still supports the expected answer.
- Some DHHS repository download entries point to `/document/.../` HTML wrappers. Never send those saved HTML bytes to the PDF parser or treat their HTTP 200 as a successful document download. The crawler resolves exactly one allowed binary attachment from the matching official document body, keeping the wrapper URL as its stable identity; missing or ambiguous attachments remain errors.
- `pipeline.parse.converter.should_parse()`, `inventory_parse_failures()`, and `build_parse_inventory_evidence()` can migrate legacy sidecar metadata as a cache-check side effect. Use all of them under the corpus writer lock. For strictly read-only diagnostics during a crawl, read JSON sidecars and the registry directly without calling these helpers.

- Copying the hosted corpus to a different root preserves absolute `/data/crawler/documents/...` paths in parse sidecars. Identity-catalog joins then report missing canonical artifacts even when source and payload hashes match. For an isolated audit, rebase only those exact paths in the disposable copy after verifying source membership and hashes; retain a transformation receipt and the original snapshot manifest. Never rewrite production metadata to accommodate an audit location.
- The pipeline image also requires versioned `packages/pipeline/data/references/cfr-supersessions.json`, not only the golden dataset. Its loader intentionally returns an empty map when missing, so Docker must include and smoke-check these rules or federal supersession edges silently disappear.
- The contracts workspace exports TypeScript source. Runtime imports from the Next.js app resolve the package export directly to `src/schemas.ts`; the old `.js` barrel re-export passes TypeScript/Vitest but fails Turbopack resolution. Run a web build or browser test after adding shared runtime constants.
- Answer release is server-enforced in the SSE adapter and the guarded LibSQL memory domain. Only server-signed final text may be recalled or cloned; a client verification part is not proof. Keep the persisted signing key when backing up application SQLite.
- Verification labels must use the final server release outcome. A `corrected` answer has passed its exact-text recheck; the old `rewrote` flag must not label it partially verified. History retains the trusted outcome without streaming confidence fields, so the label must also render from the outcome alone after reload.
- Borrowing another worktree's `node_modules` through a symlink may pass Vitest and TypeScript but fail Next.js Turbopack with "it points out of the filesystem root". Install dependencies inside the isolated worktree before browser/build checks; do not alter the original workspace's dependencies to work around it.
- Research recovery uses application checkpoints with fresh internal Mastra executions. Preserve approved edits, original limits, reserved steps, corpus release identity, and the two-recovery ceiling; never resume unchecked drafts into public reports.
- A network failure while saving a checkpoint is still transient. Only explicit checkpoint incompatibility is terminal; matching the word `checkpoint` anywhere in an error message incorrectly disables recovery after durable work has been saved.
- Mastra observational summaries can outlive the messages they summarize. Release-gated recall ignores pre-gate summaries; do not re-enable model-written working memory without verified provenance, because that tool can persist claims before the output verifier runs. Research retention/deletion must also remove Mastra workflow snapshots, which contain private intermediate data.
- A restored local Neo4j graph can predate the immutable document-ID migration even while its indexes are healthy. Run `eval-validate` and inspect its reference-integrity output before comparing answer scores; the command can exit successfully despite missing references. Use the current 55-question benchmark with the frozen evaluation-only identity catalog for both graphs. Do not substitute the historical 50-question benchmark, rewrite the graph, or match evidence by titles or policy numbers. Missing evidence remains a miss; ambiguous identities invalidate comparison.
- A healthy production release ID does not prove that the graph has the current document-ID schema. On 2026-09-22, production still used the tagged legacy graph `legacy-20260725-ae8595c`: all 112 references in the current 55-question dataset were missing, while the historical 50-question dataset's 104 references existed. Inspect the graph and deployment state before assuming the blue/green services have been bootstrapped; service definitions alone do not establish deployed graphs.
- Railway SSH can stall in the local SSH agent before authentication. For unattended inspection with an existing registered key, `IdentityAgent=none`, `IdentitiesOnly=yes`, and `BatchMode=yes` avoid that stall. Railway also caps concurrent SSH connections: do not create one SSH session per pooled Bolt connection during evaluations. Use a single shared private transport, and discard evaluation runs affected by transport failures.
- `resolveAnswerFrame` includes both routing advice and original corpus section bodies. Keep its routing reasons out of grounding evidence, but extract the section bodies as separate `corpusSection` sources; labeling the entire frame as non-evidence causes valid numeric answers to be withheld. A correction's length ratio is telemetry only: removing unsupported material can produce a much shorter valid answer, which must still pass the exact-text recheck.

- Deep-research web results must retain their retrieved snippets in private checkpoints and pass that evidence to both worker and report verification. A title and URL alone are not grounding evidence. Use a server-assigned supplementary evidence role and verifier system instructions that forbid web-only grounding of governing policy claims. Strip snippets from the public source summary, and count globally allowed portal links separately from retrieved citations.
- Corpus release policy v2 reports precision@10 and compares it with the baseline, but has no absolute precision threshold. The golden dataset has sparse relevance labels (mean 2.09 per question on 2026-09-22), so 0.9 precision at ten results is mathematically incompatible with it. Keep recall, primary-evidence hit, answer-quality/grounding, and regression gates; calibrate any future precision threshold against adequately labeled results.

- The corpus-job service can have a different `NEO4J_PASSWORD` from the production agent even when both point to legacy. For read-only legacy diagnostics, use the agent’s exact graph/model configuration through a private process environment; never print credentials or copy the entire variable map into logs.
- `policies-inactive.ncdhhs.gov` is linked by the official COVID administrative-letter index, but the hostname returned DNS failures during the September 2026 audit. DNS failure is neither HTTP 404 nor withdrawal evidence. Index classification must register every document child before excluding the index; the unresolved children still block release.
- A tombstone with zero download attempts and null payload fields may be `never_downloaded` only when retained registry/artifact snapshots and a successful encrypted-backup restore agree. A null path alone does not prove that no original existed. Keep version-1 retirement hashes mandatory and never reactivate removed rows during rediscovery.
- Source-audit collection never mutates availability counters. A resumed audit validates cached response hashes without issuing requests. Use a new audit directory for a deliberate fresh observation; do not count cache reuse as another confirmed 404.
- Generic EPSDT overview questions can route to broad CFR search and miss SSA §1905(r), leading to unsupported treatment claims. Keep the demonstrated repair in PolicyCorpus federal-authority routing and preserve the verifier’s two-pass gate. Opt-in private diagnostics use a 0700 directory with 0600 files and must never be uploaded as public release evidence.
- Observational memory may compact the current question and retrieved tool messages before final verification. The verifier must retain the authenticated newest user question and original corpus tool results in request-local server state; an observation or memory reminder is not their replacement. HTTP regressions must exercise real evidence extraction with forced observation: mocking it concealed missing evidence and verification against the framework reminder. A diagnostic process started from a production database copy also runs research recovery at startup; remove copied research state only in the disposable database before starting it, preserving the original snapshot, memory, and signing key.
- Release comparison fingerprints share the identity catalog and normalization implementation, while graph mapping hashes remain graph-specific. Require complete 55-question retrieval and answer evidence, matching catalog/configuration, untampered mapping records, and verifier telemetry before using a baseline.
- Audit evidence and classifications are part of the corpus snapshot. Keep `source-audit-evidence` in incremental backup/restore paths as well as encrypted archives. macOS tar uploads should set `COPYFILE_DISABLE=1` and `--no-xattrs` to avoid Apple metadata in Linux corpus archives.

- Production browser smoke must wait for the active sidebar thread after stream completion. The first row can still be an older same-question thread until the list refreshes, causing a false persistence failure. Match the active title exactly and reject ambiguity. Keep every result from the fixed three-attempt EPSDT gate; a verifier timeout remains a failed batch even if a later browser check succeeds.

- Pipeline lint includes both Ruff and Vulture: run `npm run lint -w @nc-medicaid/pipeline`, not only `ruff check`. New Click entrypoints can pass tests and Ruff but fail CI as unused; verify command registration, then add only those dynamic entrypoints to `vulture_whitelist.py`.

## Pipeline dead-code detection


`npm run lint -w @nc-medicaid/pipeline` runs **both** `ruff check src/` **and** `vulture src vulture_whitelist.py`. Vulture exits non-zero on *any* finding, so introducing dead Python code (or a vulture false positive) fails lint.

`packages/pipeline/vulture_whitelist.py` is a **curated** list of confirmed false positives — things vulture can't see are used: Click CLI commands (`@cli.command`), `HTMLParser` method overrides, driver/library attributes (e.g. `row_factory`), symbols referenced only by tests, and `SourceFamilyManifest` schema fields populated from `corpus-manifest.json`. If lint flags one of these for new code, add it to the whitelist.

Do **not** regenerate the whitelist with a bare `vulture src --make-whitelist` and commit it wholesale — that silently buries genuine dead code (it once would have hidden ~12 dead query constants). Use `--make-whitelist` to produce *candidates*, then triage: real dead code gets deleted, only true false positives go in the whitelist. The whitelist is excluded from ruff (`extend-exclude` in `pyproject.toml`) since its bare names would trip F821.

## Branch and worktree cleanup

Squash-merged branches can appear ahead of main even when all their work is merged. Match the branch tip to the merged PR head and inspect changes made afterward before deleting it. A merged branch can also contain valuable uncommitted work. Save dirty files, ignored non-regenerable artifacts, patches, and Git bundles before removing worktrees. See the [2026-10-02 repository audit](repository-audit-2026-10-02.md).

- `npm run test:ops` includes Linux process/lock checks requiring `flock`. On stock macOS, the Node tests can pass while the shell suite fails because `flock` is unavailable. Run the full suite in the provisioned Linux CI/image; do not treat a missing utility as evidence that the production lock algorithm failed.

- CI previously filtered PR bases to `main`, leaving stacked PRs with review checks but no technical CI. The maintenance cleanup removed that filter while preserving main push checks. Always inspect the actual check list on the exact current head before declaring a stacked PR green.
- PR qualification receipts stored only under `/tmp` may no longer exist when an old branch is resumed. Preserve source-attested evidence durably or rerun qualification; an old successful comment is not a recoverable receipt.

- Mastra minor releases can require a newer coordinated core/CLI/client/storage release set. Security maintenance pinned memory to 1.26.1 because a caret selected a newer release whose storage exports were incompatible with core 1.45.0. Group Mastra/AI updates separately and validate startup, storage, verification, recovery, builds and browser integration before adopting the group.

- A successful CLI answer does not qualify production conversational memory: the CLI deliberately constructs no `Memory` instance. The October 2026 live readiness smoke exposed memory 1.26.1 calling `patchThread` on libSQL 1.14.0, whose memory store has no such method, before answer verification. Published peer ranges permit this set, so install success also does not establish runtime compatibility. `patchThread` is inherited from core starting at 1.58.0; upgrading only the agent workspace can leave hoisted adapters using an older core. Keep a single core resolution for server adapters, and update the observability adapter for core's `flush` contract. Exercise a fresh HTTP conversation with observational memory enabled against real disposable storage when qualifying the SDK/storage set; mocked providers and CLI-only smoke can miss this contract.
- Chart recovery OCR execution requires Linux `/proc/self/fd` and descriptor safeguards. macOS lint can pass while its execution tests fail on missing Linux facilities. Use Linux CI / the pinned Docker runtime for the full suite; preserve secure descriptor-bound inputs.

- Dependency freshness checks must include the separate `e2e/package-lock.json`, the pipeline `uv.lock`/Python environment, and pinned Docker tooling. The initial 2026-10-02 configuration omitted E2E npm and Python/uv updates; dependency maintenance adds explicit coverage for both. Root `npm outdated` cannot establish that those packages are current. Compare installed Python versions with the lockfile before interpreting `uv pip list --outdated`, because ad hoc pip installations can resolve differently from the frozen uv setup now used by CI and Docker.

- Local pipeline tests can read the workstation crawler registry through unmocked release prechecks.
