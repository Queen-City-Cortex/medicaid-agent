# Verified answer release and research recovery

Chat, research reports, and the default CLI/evaluation path now share a release gate. Assistant prose remains private until claims, citations, relevance, source URLs, and quotations pass. A failed first candidate may produce one corrected answer; the exact correction gets one recheck. The default verifier is `gpt-5.6-terra` with low reasoning effort. Each provider check has a 30-second deadline and no SDK retries. A check that hits that deadline logs `verifier.deadline_aborted`; any other failed check logs `verifier.failed_closed`. Failure returns a fixed withholding notice and available sources. Minor relevance observations do not block release.

## Public answers and memory

`data-verification-status` carries `verifying`, `passed`, `corrected`, or `withheld`. The SSE adapter (`gateAnswerStream`) is an allow-list: it builds every chunk it sends from named fields and drops any chunk type it does not name, so a type added by a framework upgrade stays private until it is adopted. The stream carries:

- step and message boundaries (`start` with its message ID, `start-step`, `finish-step`, `finish`, `abort`), with no message metadata;
- tool progress: `tool-input-start`, `tool-input-available` (the tool's arguments) and `tool-output-available` (the tool's result, which the tool steps and Sources panel render);
- `tool-output-error` and `error` with fixed text. The tool's own error, which can name internal hosts, is not sent; the gate writes it to the agent log as `chat.tool_error` (the framework logs it nowhere), and that entry includes the tool's arguments;
- `data-tripwire` with the guard's `code` and fixed `userMessage`. The abort reason, which can quote a classifier, is not sent;
- `data-verification-status` with the outcome alone (`status`, `reason`, `passCount`), followed by the released answer as the only text. The verifier's findings and counts are not sent: the release outcome is the only trust signal the browser shows.

Model text and reasoning, streamed tool-argument deltas, observational-memory chunks (`data-om-*`), provider sources and files, and message metadata are dropped. Fixed application errors bypass the model-answer path.

Stored assistant messages get the same treatment whenever they are written or read: observational-memory markers keep their type and bookkeeping IDs but not the observer's text, and a failed tool call keeps a fixed error. The signature covers the released text and outcome only, so this redaction, not the signature, is what keeps other parts clean. Thread responses omit `metadata.mastra`, where the framework keeps the observer's current task and suggested response; the stored row keeps it because the framework reads it back. A thread update must therefore send the title alone: the server keeps stored metadata only when the request has no `metadata` key.

The SQLite `answer_release_keys` row signs released assistant text and its outcome. Keep this key with database backups: replacing it makes old answers untrusted. The LibSQL memory boundary guards writes, updates, reads, and clones. The same boundary fixes thread ownership: a thread write that would change an existing thread's owner is refused, and the gateway rejects the message `include` parameter, which the framework does not scope by owner. The gate classifies every method of the memory store as guarded or reviewed pass-through and the server refuses to start on an unclassified one, so a framework upgrade cannot add an unguarded read or write path unnoticed. Legacy unsigned answers become an unverified-history notice. Client messages contribute only the newest user's text and thread ID; execution settings, tool evidence, assistant history, release metadata, and resource ownership are server-controlled.

A chat thread is created by the agent, never by the browser: the gateway answers `POST /api/memory/threads` with 404, and the chat route saves the thread on the first message it accepts for a new ID, owned by the verified user and titled with the first 60 characters of the screened question. A first message refused by the identifier screen (422), the rate limit or the daily ceiling (429), or the ownership check (404) therefore leaves no thread row. A first message stopped later by an input guard leaves an empty thread with that screened title, which the owner can delete from the sidebar.

Observational memory is off by default (`OBSERVATIONAL_MEMORY_ENABLED`); the agent then recalls the thread's newest stored messages through the same guarded reads. When it is turned on it ignores summaries created before the release gate and rebuilds from guarded messages. The model-written working-memory/profile tool is disabled because its writes happen before answer verification.

The chat route also reads the newest stored turns of the owner's thread through the guarded store and sets them on the server-owned `chatPriorTurns` request-context key for the coverage boundary and the scope gate, overwriting any client value. A gate therefore sees an earlier answer only as released text or the unverified-history notice. Stored turns are not screened for identifiers again: each was screened when it was sent.

Production rejects `VERIFIER_ENABLED=false`. Local CLI debugging may still explicitly opt out; that output must not be treated as released application content.

## Durable research

Migrations 5 and 6 add the signing key, approved decision, original limits, corpus identity, checkpoint version, recovery count/schedule, verification result, source summaries, checkpoints, and consumed-step counters. Deployment remains one agent service with its existing SQLite volume.

Private checkpoints cover planning, each worker's draft/evidence and verified result, reflection decisions, synthesis, verifier passes, and the released report. Public status never returns the draft. A worker result is saved as it completes, without waiting for its siblings. Stable question hashes avoid duplicate results. Plan approval can only remove proposed sub-questions: the decision names the kept ones by position in the stored plan (`keptSubQuestions`) and carries no question text, so nothing the client writes at approval is researched. A position outside the plan, an empty or repeated list, or any other field is refused with 400 `invalid_decision` and the run keeps waiting. The approved subset is committed atomically with execution ownership before resume.

A worker draft that fails grounding is not released and no longer ends the run. Its sub-question becomes a gap: the report's `workerFailures` entry carries the sub-question text and one fixed notice (`RESEARCH_GAP_NOTICE`), the writer is given the sub-question text only and told to state it as unresolved, and the report is verified against the findings that passed. The draft stays in its private checkpoint, and only the report step publishes a verification outcome and source list for the run. Failed grounding is still terminal for the final report and when more than half of a batch of workers (the approved plan, or one round of follow-ups) has no verified finding, which includes every worker being withheld. A verifier outage on a worker is not a gap: it goes to recovery when retryable and otherwise ends the run.

The planner, worker and report-writer agents retry a failed provider call twice (`maxRetries: 2`, after 1 and 2 seconds). The retry happens inside one reserved step, so a rate limit or 5xx spends neither a second step nor a recovery claim; a call that still fails goes to run recovery. The verifier keeps zero retries.

Recovery starts a fresh internal Mastra execution under the same public run ID and reuses checkpoints. Waiting plans still require approval. Provider steps are reserved before dispatch; ambiguous interruptions do not restore the budget. Recovery consumes actual new usage but does not create another daily research start.

Two per-user limits apply over a rolling 24 hours, both counted from each run's creation time and both enforced in the single statement that creates a run. A user gets two research reports: a run consumes one once its plan is approved, and keeps it whether the run then completes, fails or is cancelled, because the workers have already spent model calls. A plan that is declined, cancelled before approval, left to expire after 24 hours, or never produced because planning failed consumes no report. Because the planner runs before approval, every created run also counts toward a cap of six plans, which is what stops a create-and-cancel loop. A refused start returns 429 with `research_daily_quota` (reports) or `research_planning_limit` (plans), a `Retry-After` header and `retryAt`, the time the limit next admits a start; the web client shows it as a notice with that time. One active run per user (409 `active_research_run`) and the shared per-user message rate limit on `POST /research/runs` still apply.

The lease remains 15 minutes with one-minute renewal/sweep. Claims are atomic and mutations require the current, unexpired owner. There are at most two recovery claims over the entire run. Transient failures become eligible after 30 seconds, then two minutes; a local timer starts eligible work, with the sweep covering process restarts. Expired leases become eligible immediately when swept. Concurrency still limits actual execution.

Authentication/configuration errors, incompatible checkpoints, exhausted budgets, changed corpus releases, and failed grounding of the final report or of more than half of a worker batch are terminal. A verifier outage retries the saved draft; exhaustion leaves it withheld. A missing corpus release ID cannot be used for recovery. Cancellation clears scheduled retries and prevents late results from publishing. The run is marked cancelled before its Mastra workflow is cancelled; if that second step fails (an expired plan, a declined plan or a user cancel), the recovery sweep retries it every 60 seconds for a day, and retention removes the snapshot after that. In the browser a run is cancelled only by the Cancel, Start over and Try again controls in the Deep Research view: switching conversation or turning the Deep Research pill off leaves it running, and the pill then shows "running", "plan ready" or "report ready".

Retention and account deletion remove private checkpoint/budget rows and associated Mastra workflow snapshots before deleting the public run. Account deletion has no route or scheduled job: an operator runs the command in the [runbook's account deletion procedure](../../RUNBOOK.md#data-classification--retention), which prints the statements `AppDatabase.deleteUserData` runs for `sqlite3` on the agent volume. Conversation retention deletes an expired thread's messages, thread state and thread-scoped observational-memory record with it, and sweeps records older than the cutoff whose thread no longer exists. Existing completed research reports without a verification result are withheld when read.

## Verification records

Each chat answer, released or withheld, leaves one private row in `answer_audit` (migration 8), keyed by the stored assistant message id, which is the id the stream's `start` chunk and thread history give the browser and the id feedback is filed under. The row holds the outcome, the verifier telemetry, the findings of each pass, the verifier's token usage, the configured `CORPUS_RELEASE_ID` and the agent model. It does not hold the question, the draft, the model's correction or the evidence text. The findings are the verifier's own words about a draft and quote short excerpts of it (each capped at 500 characters, 50 per list), so they are unverified model prose: no route returns them, the stream gate has no field for them, and the row is deleted with its conversation, with the account, and 90 days after it was written. An operator reads it with `sqlite3` as the [runbook](../../RUNBOOK.md#data-classification--retention) shows.

`HallucinationVerifier` writes the row and one `usage_events` row per verifier call (route `chat`, phase `verifier`) through the two stores passed to its constructor. Neither write is awaited and each catches its own failure, so the record cannot delay or fail a release. An answer with no stored owner (no thread or user on the message) writes neither. Two outcomes leave no row: a turn the stream gate withholds itself because the processor never reported (`unavailable`, pass count 0), and a turn stopped by an input guard, which the verifier never sees. Deleting a thread from the sidebar deletes its rows and its feedback through the memory gate's `deleteThread` wrapper; the daily retention run also sweeps rows whose thread is gone once they are an hour old, in case that delete failed.

## Operational checks

Structured logs include `chat.verification` (thread id, message id, outcome, passes, reason and latency for a chat answer; ids only), `verification.release` (outcome, passes, reason, latency; shared with research and the CLI, so it has no ids), `deep_research.checkpoint_reused`, `deep_research.recovery_scheduled`, `deep_research.recovery_claimed`, `deep_research.sub_question_gap` (reason only), and `deep_research.terminal_failure` with a failure category. CLI `---VERIFIER---` JSON carries `outcome`, `pass_count`, `withholding_reason`, `latency_ms` and the per-check counts. It no longer has `confidence`, `severity`, `pure_marker_fallback` or `substance_loss_fallback`: the score could not describe a released answer and the two flags were always false. The evaluation harness reads none of the four.

Citation section labels are measured and not enforced. `verifier.unknown_sections` is logged, and `unknown_section_count` set in the `---VERIFIER---` JSON, when the last text checked cites a numbered section (`§ 5.2.1`, `§ 441.302`) and the turn retrieved neither that section's text nor a parent's under the same link. The log line holds the outcome status, the count and the label and link of each distinct citation; it never holds the question or the answer. It does not change the outcome. On the 2026-09-22 final gate the rule flagged none of 200 numbered labels. Before making it a release condition, read the logged labels on `passed` and `corrected` answers and replay the rule on evidence from the current corpus; see the [gotchas](../development/gotchas.md).

Before production release, compare a stable, full answer-evaluation dataset on the same corpus/model configuration against the baseline. Report passed/corrected/withheld proportions, withholding reasons, answer scores, and median/p95 verification latency. Run repeat samples where judge variance matters. Do not accept a lower withholding rate by weakening grounding checks.

Validation on this branch uses real Mastra execution and temporary file-backed SQLite with mocked providers, including interruption after planning, approval, individual workers, reflection, synthesis, verification, and final report persistence. It checks replay without repeated model calls, preserved approval, bounded retries, verifier-outage recovery, lease contention, cancellation, budget exhaustion, corpus/version incompatibility, cleanup, and draft-sentinel exclusion from SSE, memory, clones, and the UI. Mocked browser tests cover reloads and thread switching. Research reload restores only the public run ID from session storage and polls the owned endpoint; it never re-approves a plan.

Final local checks: 387 agent tests, 271 web tests, 4 contracts tests, and 38 mocked browser tests passed. Agent/web builds, affected type checks, and lint passed. All nine Neo4j integration tests passed against a disposable database after Docker became available.

The [live validation report](../validation/verified-release-2026-09-22.md) records the matched 50-question baseline, initial gate results, corrective changes, and final comparison. The initial gate withheld 30% of answers, exposing evidence-formatting and verifier-calibration problems that were corrected before the final rerun. The local graph predates the immutable-ID migration, so the comparison uses the matching historical dataset. A follow-up against the tagged production graph passed five matched answer checks and a live research run with two automatic recoveries, without repeating completed model calls. Production still lacks all 112 evidence references in the current 55-question dataset; deployment remains blocked on a validated current corpus. Use an isolated observability DB for evaluation (`MASTRA_OBSERVABILITY_PATH=:memory:`) and run the pipeline CLI from `packages/pipeline`.
