## ARCH-1 · A past answer's verifier findings cannot be recovered, and chat verifier cost goes unrecorded

Severity medium · effort M

### architecture-06 — The owner cannot reconstruct why an answer was withheld or wrong: only a reason code is stored, and the log line carries no identifiers

- **Location:** `packages/agent/src/processors/verifier/run.ts:166`
- **Severity:** medium · **Kind:** design · **Effort:** S · **Status:** confirmed
- **Claim:** In the default deployed configuration, the web chat path computes a 25-field telemetry object and the unsupported and missing-citation claim lists on every turn and persists none of them. What survives is one `verification.release` log line (status, reason, passCount, latencyMs; no run, thread, user or message id) and message metadata holding the outcome (status, reason, passCount) plus an HMAC signature. Confidence, severity and counts are streamed to the client but not stored. Traces are off by default in production. Chat-path verifier token usage is never recorded, because processor.ts omits `onUsage` and the verifier's `generateObject` call is outside the agent's `totalUsage`; deep research records both verifier usage and per-pass checkpoints. Exception: an opt-in operator mode (`VERIFIER_PRIVATE_DIAGNOSTICS_DIR`, documented for explicit diagnostic runs only and not set in the Dockerfile) writes the draft, evidence, per-pass verifier findings and telemetry to local 0600 JSON files. Those files are keyed only by a server-generated diagnosticId, with no thread, run, user or message id and no corpus release id or retrieval mode, and they sit on ephemeral container disk. So "not stored anywhere" should read "not stored unless private diagnostics were enabled beforehand, and even then not joinable to a thread or user."
- **Evidence:** packages/agent/src/processors/verifier/run.ts:166 `log.info('verification.release', { ...outcome, latencyMs: Date.now()-started });`; packages/agent/src/processors/verifier/processor.ts:90 `if (!writer) emitVerifierTelemetry(telemetry);` (the streaming path always has a writer); processor.ts:83 calls runVerificationForAnswer without onUsage, while deep-research/workflow.ts:197 passes `onUsage: usage => recordResearchUsage('verifier', getVerifierConfig().model, { usage }),`; packages/agent/src/answer-release.ts:25 `metadata: { ...content.metadata, answerRelease: { outcome, signature: signature(text, outcome) } },`; packages/agent/src/runtime-config.ts:100 `const traceStore = nonEmpty(env, 'TRACE_STORE') ?? (production || options.cli ? 'off' : 'duckdb');`
- **Impact:** A legal-aid attorney reports a wrong answer with a thumbs-down. The owner can read the released text and the tool results kept in the thread, but not which verifier findings were waived as minor, whether retrieval was degraded, which corpus release or model produced it, or (for a withheld answer) which claim failed; the only way to learn is to re-run a paid, non-deterministic turn. Withholding-rate and latency trends cannot be joined to threads or users, and usage_events understates chat cost by the whole verifier (same model as the agent by default, up to two passes over about 120k characters of evidence).
- **Fix:** Keep the single private table, but trim it and close the deletion and id gaps. 1. **Table (migration version 7).** `answer_audit(message_id TEXT PRIMARY KEY, thread_id, resource_id, created_at, outcome_json, telemetry_json, findings_json, corpus_release, agent_model)`. - `telemetry_json` is the existing `VerifierTelemetry`, which already carries verifier model, latency and counts. - `findings_json` is `verification.unsupportedClaims`, `missingCitationClaims` and `relevanceIssues`. - Leave out retrieval mode and source keys/links (already in the thread's stored tool-invocation parts) and build SHA (add later only if a SHA env var is actually wired). 2. **Write path.** Inject `{ usageRepo, auditRepo }` into `new HallucinationVerifier(...)` at index.ts:139.
