The brief's per-token concern does not apply to prose, because the server releases the answer in a single delta, but the cost is paid on tool events and on typing.
- **Evidence:** packages/web/src/app/chat/page.tsx:45 `const [input, setInput] = useState('');` in the component that renders `<MessageList` (:280); packages/web/src/components/MessageList.tsx:439 `export function MessageList({ messages, isStreaming, status, onRerun, ...` and AssistantMessage (:142) are plain functions; each AssistantMessage render recomputes :174-177 `const { ordered: sources, citedCount } = splitSourcesByCited(` / `extractMessageSources(msg),` / `extractCitedUrls(msg),` / `);`, :222 `const resolveCitation = buildCitationResolver(sources);` and :426 `content={buildAnswerClipboardText(finalAnswerText, sources)}`; useChat is created without experimental_throttle (packages/web/src/lib/use-chat-thread.ts:99-104) and packages/web/next.config.ts:5-8 does not enable the React Compiler. Probe (real ChatPage and MessageList; react-markdown and extractMessageSources wrapped with counters): '20 answers on screen, 10 keystrokes -> ReactMarkdown renders: 200 (20/keystroke), extractMessageSources calls: 200 (20/keystroke)'. With real react-markdown, 8 tool results and a ~1.6 KB cited answer per turn: 16.2 ms per keystroke at 5 turns, 53.8 ms at 20, 128.3 ms at 50.
- **Impact:** Typing a follow-up in a long thread gets laggy: the measured cost is already at the 16 ms frame budget with five answered turns in jsdom on a fast laptop and grows linearly; older phones and Chromebooks, which beneficiaries and case managers use, will be several times slower. The same work runs for every tool-call chunk of a new answer, together with the remount of every citation link described in the accessibility finding.
- **Fix:** Do it in two small steps, both inside packages/web/src/components/MessageList.tsx plus one callback in chat/page.tsx. Leave the input state where it is. 1. **Typing and the corpus poll (one line).** Export MessageList as `memo(function MessageList(...))`. All of its props from ChatPage are already referentially stable across keystrokes, and the probe shows this alone takes the cost from 20 markdown renders and 20 source extractions per keystroke to 0. 2. **Stream chunks and feedback updates.** Wrap AssistantMessage in React.memo and make its props stable: - Drop the `messages` prop. MessageList already walks the array, so have it compute the preceding user index and pass `userIndex`, or pass a bound rerun. - Pass `feedback={feedbackMap[msg.id]}` in place of the whole map. - Make ChatPage's handleRerun independent of `messages`, by reading the latest messages from a ref or having rerunAnswer take ids. Today it is recreated every chunk. - Ideally make the use-feedback callbacks independent of `feedbackMap`, using functional setState or a ref. The installed useChat keeps earlier message objects identical across chunks, so only the streaming message re-renders. 3. **Lock it in.** Add the render-count probe as a real test: N answers, type K characters, expect 0 ReactMarkdown renders. Skip the rest of the original list: - Moving input state into ChatInput: unnecessary after step 1, and it complicates the restore-on-failed-send path. - Per-message useMemo, clipboard-on-click and hoisting the markdown components object: redundant once AssistantMessage is memoised. - experimental_throttle: prose arrives as one delta, so there are only a few tool events to throttle. - React Compiler: new build dependency and Babel pass; revisit under #144 if at all. - Windowing: wait until real threads show a need.
